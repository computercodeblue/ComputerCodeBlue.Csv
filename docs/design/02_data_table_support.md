# DataTable support

Status: **Implemented.**

## Motivation

Some consumers (reporting tools, legacy ADO.NET code, anything binding to a
`DataGridView`/`DataTable`-based UI) want a CSV file loaded straight into a
`System.Data.DataTable` rather than a typed record or a dictionary-per-row.
`Read<T>`/`ReadDynamic` don't fit that case well — the caller would have to
build the `DataTable` by hand, row by row, duplicating what ADO.NET already
does for any `IDataReader`.

## Background: what already works today

CsvHelper ships `CsvHelper.CsvDataReader`, an `IDataReader` adapter over
`CsvReader`, specifically so CSV data can be fed into anything that consumes
`IDataReader` — `DataTable.Load(IDataReader)`, `SqlBulkCopy`, etc. This is
exactly the "forward to CsvHelper, don't reimplement" case the project
prefers: the whole feature is a few lines of adapter wiring around two BCL/
CsvHelper primitives, not a hand-rolled CSV-to-DataTable builder.

## Verified behavior (empirically, against CsvHelper 33.1.0)

Confirmed by running `DataTable.Load(new CsvDataReader(csv))` directly
(source also cross-checked against CsvHelper's `CsvDataReader.cs`):

### 1. Loading into an empty `DataTable` creates all-`string` columns

`CsvDataReader.GetFieldType(int)` unconditionally returns `typeof(string)`.
There is no numeric/date type inference — a CSV value is text, and it stays
text unless the caller says otherwise (see #2). This is actually a
*feature*, not a gap: it's what keeps `"07030"` a zip code instead of
becoming `7030`, consistent with how `ReadDynamic` already treats
untyped/dynamic reads elsewhere in this library.

### 2. Loading into a pre-typed `DataTable` converts values to the existing column types

If the caller passes in a `DataTable` that already has typed columns
(hand-built, or generated by a typed `DataSet` designer), `DataTable.Load`
matches columns by name and converts each incoming string value to the
existing column's type. Verified: a table with an `Age` column typed `int`
ends up with real `Int32` values after `Load`, not strings. A bad
conversion (e.g. `"abc"` into an `int` column) throws — consistent with
this project's "prefer explicit failures" stance; no extra try/catch is
added around it.

This means one method covers both the "just get me a table" case (pass an
empty `DataTable`) and the "load into my existing schema" case (pass a
pre-typed one), entirely through `DataTable.Load`'s existing behavior — no
extra API surface needed for it.

### 3. `CsvOptions.HasHeaderRecord = false` works, but produces `Column1`/`Column2`/... column names

`CsvDataReader` doesn't require a header row (verified: it checks
`HasHeaderRecord` before calling `csv.ReadHeader()`, so it doesn't throw).
Without a header, `DataTable.Load` falls back to its own default column
naming. This is existing ADO.NET behavior, not something this library needs
to special-case — just worth documenting so it isn't a surprise.

### 4. `CsvDataReader.Dispose()` disposes the underlying `CsvReader`

Confirmed in source (`csv.Dispose()` inside `Dispose()`). The
`using stream / using reader / using csv / using dr` chain used elsewhere
in this codebase (`CsvFile`, `CsvStream`) works unchanged here; no special
disposal handling needed.

### 5. An empty/header-only file behaves the same as it does for `Read<T>` today

Zero data rows just yields zero `DataTable` rows with the right columns. A
completely empty file with `HasHeaderRecord: true` (the default) throws
CsvHelper's usual "no header record" `ReaderException` — the same failure
mode `CsvFile.Read<T>` already has on an empty file, not a new edge case
introduced by this feature.

## API shape: extension method on `DataTable`, not a `CsvFile`/`CsvStream` addition

This is a deliberate departure from the naming pattern used by every other
method in the library (`CsvFile.Read<T>(filePath, ...)`,
`CsvStream.Write<T>(stream, ...)`), which name the static class after the
*source*/*destination* (file or stream) and hang the CSV verb off it. Here
the natural anchor is the *destination type*, `DataTable`, for two reasons:

- It mirrors the BCL's own idiom — `DataTable` already has
  `Load(IDataReader)`. A `LoadCsv` extension reads as "the CSV-flavored
  version of the method already on this type," which is more discoverable
  via IntelliSense on a `DataTable` instance than a same-named static class
  method would be.
- The pre-typed-merge behavior (#2 above) only makes sense against an
  *existing* `DataTable` instance the caller already owns — a static
  factory method (`CsvTable.Load(filePath) : DataTable`) can't express
  that without a second overload taking a `DataTable` parameter, which is
  more API surface for the same capability.

`LoadCsv` (not `Load`) avoids colliding with/shadowing the BCL's own
`DataTable.Load` overload set in IntelliSense.

**Return value:** `LoadCsv`/`LoadCsvAsync` return the same `DataTable`
instance (`this`) rather than `void`, unlike `DataTable.Load` itself. This
is a deliberate, minor deviation for ergonomics — it lets the common
"just get me a table" case be a one-liner:

```csharp
var table = new DataTable().LoadCsv("people.csv");
```

without adding a second "create and load" method to the public surface.

## Proposed API

Mirrors the existing file/stream split (`CsvFile`/`CsvStream`), added as a
new `DataTableExtensions` static class:

```csharp
public static class DataTableExtensions
{
    /// <summary>
    /// Loads the file at <paramref name="filePath"/> into <paramref name="table"/> using
    /// <see cref="DataTable.Load(System.Data.IDataReader)"/>. If <paramref name="table"/> has no
    /// columns, columns are created (all typed <see cref="string"/>) from the CSV header. If
    /// <paramref name="table"/> already has columns, values are matched by column name and
    /// converted to each column's existing type.
    /// </summary>
    public static DataTable LoadCsv(this DataTable table, string filePath, CsvOptions? options = null);

    /// <inheritdoc cref="LoadCsv(DataTable, string, CsvOptions?)"/>
    /// <remarks>The stream is left open; the caller remains responsible for disposing it.</remarks>
    public static DataTable LoadCsv(this DataTable table, Stream stream, CsvOptions? options = null);

    /// <inheritdoc cref="LoadCsv(DataTable, string, CsvOptions?)"/>
    public static Task<DataTable> LoadCsvAsync(this DataTable table, string filePath, CsvOptions? options = null, CancellationToken ct = default);

    /// <inheritdoc cref="LoadCsv(DataTable, Stream, CsvOptions?)"/>
    public static Task<DataTable> LoadCsvAsync(this DataTable table, Stream stream, CsvOptions? options = null, CancellationToken ct = default);
}
```

Implementation (file overload shown; stream overload is the same shape with
`leaveOpen: true`, matching `CsvStream`'s existing convention):

```csharp
public static DataTable LoadCsv(this DataTable table, string filePath, CsvOptions? options = null)
{
    var config = CsvOptionsAdapter.ToCsvConfiguration(options ?? CsvOptions.Default);

    using var stream = File.OpenRead(filePath);
    using var reader = new StreamReader(stream);
    using var csv = new CsvReader(reader, config);
    using var dr = new CsvDataReader(csv);

    table.Load(dr);
    return table;
}

public static Task<DataTable> LoadCsvAsync(this DataTable table, string filePath, CsvOptions? options = null, CancellationToken ct = default)
    => Task.Run(() => table.LoadCsv(filePath, options), ct);
```

`LoadCsvAsync` forwards to the sync method rather than duplicating the
read logic — there's no CsvHelper/ADO.NET async path here to make genuine
use of (see below), so a second implementation would just be the same code
twice.

### Async caveats worth documenting on the method itself

Neither `IDataReader` nor `DataTable.Load` has an async surface (unlike
`DbDataReader`), so `Task.Run` isn't a shortcut around a "better" async
option — it's the only one available, and this is the standard pattern for
giving sync-only work an async signature. Two consequences worth stating
in the XML doc so callers don't assume more than it does:

- **No server-side throughput benefit.** This offloads the work to a
  thread-pool thread; it doesn't overlap I/O the way `ReadAsync` does. It's
  useful for keeping a UI thread responsive, not for scaling concurrent
  server load.
- **`ct` only prevents starting the work, not cancelling mid-load.** Once
  `Task.Run`'s delegate starts executing, `DataTable.Load` runs to
  completion; there's no per-row cancellation checkpoint like
  `CsvFile.ReadAsync` has. This is weaker than this library's other async
  methods, so it should be called out explicitly rather than left implicit.

## Non-goals

- No `LoadOption` parameter (`PreserveChanges`/`OverwriteChanges`/`Upsert`).
  `DataTable.Load(IDataReader)`'s default is used. Can be added later as an
  additive overload if a real need shows up — not speculative surface for
  now.
- No CSV-from-`DataTable` write direction (`WriteCsv`/`table.WriteCsv(...)`)
  in this change. `DataTable.CreateDataReader()` (BCL) could feed a similar
  writer-side helper, but that's a separate, symmetric feature with its own
  design questions (e.g. `DBNull` handling) — out of scope here.
- No attempt to infer richer column types (int/DateTime/etc.) when loading
  into an empty `DataTable`. `CsvDataReader` reports every column as
  `string` by design (see #1); working around that would mean reimplementing
  type inference CsvHelper deliberately doesn't do for dynamic/untyped
  reads. A caller who wants typed columns pre-builds the `DataTable` schema
  (see #2) — the existing mechanism already covers it.

## Testing plan

- `LoadCsv(string)`/`LoadCsv(Stream)`: basic load into an empty `DataTable`
  — correct column names, all columns typed `string`, a leading-zero value
  (e.g. a zip code) round-trips unchanged.
- Load into a pre-typed `DataTable` (e.g. an `int` column): values land
  converted to the declared type, not as strings.
- `HasHeaderRecord = false`: load succeeds; columns get ADO.NET's default
  names.
- Empty/header-only file: zero rows, correct columns, no exception.
- Completely empty file with `HasHeaderRecord: true` (default): throws,
  same as `CsvFile.Read<T>` does today on an empty file.
- Stream overload leaves the stream open after `LoadCsv` returns (mirrors
  the existing `CsvStreamTests` pattern of asserting the stream is still
  usable/positioned as expected afterward).
- `LoadCsvAsync`: round-trips the same data as the sync method; passing an
  already-cancelled `CancellationToken` throws before any work starts.
- Use `MemoryStream` for the stream-based tests and `TempCsvFile` (existing
  test helper) for the file-path-based tests, consistent with the rest of
  the test suite.
